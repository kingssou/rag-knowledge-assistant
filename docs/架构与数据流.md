# 架构与数据流

## 全链路

```text
文档(txt/md/pdf/docx)
   → 解析与清洗（loader.py）
   → 分块，含重叠与元数据（chunker.py）
   → Embedding（hash / sentence-transformers / openai）
   → Chroma 持久化索引（ingest/pipeline.py）

用户问题
   → 向量召回（Chroma cosine）
   → 关键词召回（BM25 全库计算）
   → 分数归一化后加权融合（alpha 控制权重）
   → 查询词覆盖率重排序（rerank）
   → Prompt 组装（强制引用编号 + 资料不足时拒答）
   → LLM 生成（mock / openai / ollama）
   → 引用解析与置信度判断
   → 答案 / 拒答
```

## 为什么用混合检索

- 纯向量检索对专有名词、编号、数字这类精确词召回不稳定；
- 纯 BM25 无法召回语义相近但用词不同的表述；
- 两者分数归一化后加权，可以让「远程办公超过三天」这种既含数字又含语义的问题同时受益。

## 为什么默认模式是 hash + mock

不是为了效果，是为了让项目**在没有 API Key、没有显卡、没有网络的机器上也能完整跑通**，从而可以：
1. 本地演示全链路；
2. 跑确定性单测和回归评估；
3. 面试时随时切换真实模型，证明适配器设计是有效的。

切换到真实模型只需环境变量，不需要改代码：

```bash
EMBED_MODEL=sentence-transformers LLM_MODE=ollama python main.py init --reset
```

## 目录职责

| 目录 | 职责 |
|---|---|
| ingest | 文档解析、清洗、分块、入库 |
| retrieval | Embedding、混合召回、重排序 |
| generation | Prompt、LLM 适配、带引用生成、拒答 |
| evaluation | 评估集、指标、批量评估与报告 |
| api | FastAPI 服务层 |
| deploy | Docker 与 Compose 部署 |
| data/sample_docs | 演示用示例文档 |
| tests | 核心逻辑单测 |
